Moves the photos off a phone and onto a computer, finds the duplicates by content rather than
by name, frees the space they were taking, and can leave the result in an encrypted archive.

Context

A tool of my own, not coursework. When a phone fills up the options are paying for cloud
storage every month, deleting things by hand, or moving them somewhere yourself. This is the
third one, automated, so that "I will sort the photos out one day" stops being a decision.

The problem

Copying is the easy part. The problem is knowing what you already copied.

Photos change name as they move between devices: the same picture is IMG_0421.jpg on the
phone and 20240613_182233.jpg on the computer. Compare by name and you copy it twice.
Compare by size and two different photos of the same burst look identical. And you cannot
delete anything from the phone until you are sure, byte for byte, that it is somewhere else.

The solution

Identity is the content, not the name. Every file is reduced to the MD5 of its bytes, so
a photo that was renamed on the way is still recognised as the same photo, and two different
files that happen to share a name are not confused. That is what makes it safe to delete from
the source afterwards.

Deleting is a budget, not a switch. Rather than "delete duplicates", you say how much
space you want back — ALL, 5GB, 50% — and it deletes the largest duplicates first until
it gets there. You free what you needed and keep the rest where it is.

Nothing is deleted that is not somewhere else. The clean step only ever considers files
that are already in the destination, checked by hash if you ask for it.

The archive is encrypted with AES-256, through gpg, and the password is fed in over a
pipe. Both details matter: the previous version used zip -P, which is ZipCrypto — broken
for decades, and recoverable from a single known file inside the archive — and it passed the
password as a command-line argument, where anyone running ps could read it.

Layout

media-manager.sh          the flow: copy, compare, clean, archive, encrypt
src/copy_images.py        copies, skipping what is already there by hash
src/compare.py            reports what is in one side and not the other
src/clean.py              deletes duplicates from the source, up to a budget
paths.txt                 source on line 1, destination on line 2
tests/test_flow.sh        the whole flow over throwaway folders
docs/connecting-a-phone.md   mounting an iPhone or Android, and Windows paths

Requirements

  • A POSIX shell, zip and gnupg
  • Python 3.12, standard library only
  • For a phone: ifuse, usbmuxd and libimobiledevice on iPhone. See
    docs/connecting-a-phone.md

Build and run

Put the two paths in paths.txt:

/home/you/iphone/DCIM
/home/you/Pictures/phone

Then pick how much you want it to do:

./media-manager.sh                       # everything, asking as it goes
./media-manager.sh --comparar            # only report the differences
./media-manager.sh --zip                 # copy, compare and archive
./media-manager.sh --zip --encriptar     # and encrypt the archive
./media-manager.sh --limpiar --zip --encriptar   # the lot

One step at a time, when you know what you want:

./media-manager.sh --only-copiar
./media-manager.sh --only-comparar
./media-manager.sh --only-limpiar
./media-manager.sh --only-zip
./media-manager.sh --only-encriptar backup_20240613_182233.zip   # or the latest one

Decrypting is plain gpg, with nothing of this tool involved:

gpg -d -o photos.zip backup_20240613_182233.zip.gpg

Running the tests:

sh tests/test_flow.sh

The duplicate in that run is a copy of uno.jpg renamed to IMG_9999.jpg: it is the case
the whole tool exists for, so it is the one the test insists on.

What I learned

  • Hashing the content is the entire idea, and it is six lines. Everything else in the tool is
    the interface around that one decision.
  • "Free 5 GB" is a better question to ask a user than "delete duplicates?". The second one
    demands a leap of faith; the first one has an answer you already know.
  • Shipping encryption is easy to get wrong in a way that still looks like it works. zip -P
    produced a file that asked for a password, so it looked encrypted, and was not.
  • Limitations:
    • MD5 is the right tool here — it identifies files, it is not guarding against anyone — but
      it would be the wrong one if the point were to detect tampering.
    • The copy step reads a whole directory tree into memory before it starts. Fine for a phone,
      not for a NAS.
    • There is no dry run: the clean step tells you what it will delete and asks, and that is
      the only brake.
    • The messages and the options are in Spanish, which is how I use it.
