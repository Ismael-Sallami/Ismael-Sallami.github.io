An adversarial-search player for ParCheckers, a deterministic Parcheesi variant where each
player owns two colours and picks which die to use every turn.

Context

Coursework for Inteligencia Artificial, year 3 of the double degree in Computer Science
and Business Administration, University of Granada (2024-25). Solo work.

The game engine, board model, dice, turn management and GUI are course-provided material
and are not in this repository. What is here is the file the assignment asks you to write:
the AI player.

The problem

The player has to choose a move before a time limit, and within a cap on generated and
evaluated nodes that the framework enforces (NodeCounter). Each turn it picks a colour, a
piece and one of the available dice. Three built-in opponents ("ninjas") are the benchmark:
the score is out of 6, because there are three ninjas and each match is played twice, once
starting and once receiving.

The solution

Minimax with alpha-beta pruning, and four search variants layered on top of it. think()
selects one by player id, so the same file can be compiled once and run as four different
players:

id Search Heuristic
0 Alpha-beta ValoracionTest
1 Alpha-beta + probabilistic pruning + quiescence HeuristicaMejorada
2 The above + move ordering + dynamic depth HeuristicaMejorada
3 Alpha-beta PruebaH

The pieces that do the work:

  • Alpha-beta to depth 8 (PROFUNDIDAD_ALFABETA), against depth 4 for plain minimax.
  • Probabilistic pruning. Instead of cutting only when alpha >= beta, it also cuts when
    beta - alpha < epsilon (0.3 by default). Trades a little accuracy for depth.
  • Move ordering. Children are sorted by the heuristic, descending in MAX and ascending
    in MIN, so the bounds tighten earlier and more branches get cut.
  • Dynamic depth. The depth is raised or lowered from the branching factor of the node
    (UMBRAL_RAM_BAJA 3, UMBRAL_RAM_ALTA 8), to spend the time budget where the tree is
    narrow.
  • Quiescence search up to 3 extra plies (MAX_PROFUNDIDAD_QUIETUD) at the leaves,
    following only tactical moves, so the search does not stop right before a capture.
  • Weighted heuristics. Progress to goal, pieces on safe squares, pieces home, own and
    enemy barriers, and threat of capture, each with its own weight constant.

Chance is part of the game, not an extra layer: the die is one more branch in the tree,
because the framework exposes which dice are available in the current state.

Layout

src/AIPlayer.cpp   the engine, 1,467 lines: searches, heuristics and think()
src/AIPlayer.h     class declarations, including the six Heuristic subclasses
docs/report.pdf    the write-up handed in, with the reasoning behind each variant

Requirements

  • A C++17 compiler (g++ 11 or later).
  • The ParCheckers framework of the subject, which provides Parchis.h, Player.h,
    Heuristic.h, Attributes.h and NodeCounter. It also needs SFML for the GUI.

Build and run

This repository does not build on its own, and it is not meant to: without the framework
there is no Parchis class to search over. To run it, drop these two files into a checkout
of the course framework, where the assignment expects them:

cp src/AIPlayer.cpp src/AIPlayer.h <framework>/src/personal/
cd <framework> && ./install.sh          # builds with cmake and SFML
./build/parchis --p1 0 --p2 1           # player ids pick the variants of the table above

The include paths in AIPlayer.h are relative (../../include/model/...), so the files
have to sit in src/personal/.

What runs here without the framework is the static analysis:

cppcheck --std=c++17 --enable=warning,style,performance --suppress=missingInclude src/

Results

From the write-up, playing the full round against the three ninjas both as first and second
player:

id Search Heuristic Score
1 Alpha-beta + probabilistic + quiescence HeuristicaMejorada 4 / 6
3 Alpha-beta PruebaH 3 / 6
2 Alpha-beta + probabilistic + ordering + dynamic depth HeuristicaMejorada 1 / 6

The best player is not the one with the most machinery. Stacking ordering and dynamic depth
on top of probabilistic pruning made each move slower, and the extra cost bought nothing
because the heuristic, not the search, was the limit.

What I learned

  • A cheap heuristic with a plain alpha-beta beat more ninjas than an elaborate heuristic with
    four optimisations on top. Search depth cannot fix an evaluation function that measures the
    wrong thing.
  • Move ordering only pays off when the heuristic ranks moves well. Sorting by a mediocre
    evaluation reorders the tree without improving the cut-offs.
  • Limitations of what is here, kept as handed in:
    • think() has no default branch. With an id outside 0–3 no search runs and no move is
      chosen. The four ids used in the assignment are covered, nothing else is.
    • valor is assigned in every branch of think() and never read.
    • Several searches and heuristics (Minimax, Minimax_Limitado, Heur1, Heur2,
      HeuristicaNueva, Poda_AlfaBeta_Mejorada) are experiments that think() never calls.
      They stayed in on purpose, so the write-up could point at them.
    • Some weights are non-const globals that ajustarPesosDinamicamente mutates, while
      think() is declared const. It works because one process plays one game, and it would
      not survive two searches running at once.
    • Identifiers and comments are in Spanish, the language the subject is taught in.
