An abstract data type for grayscale images in C++, with the six programs that exercise it
and an efficiency study of the one operation whose cost is not obvious.

Context

Coursework for Estructuras de Datos, year 2 of the double degree in Computer Science and
Business Administration, University of Granada (2023-24).

The problem

Write the Image type from scratch: no vector, no smart pointers, a raw buffer of bytes
managed by hand. It has to read and write PGM, expose pixels in two ways, and support six
operations that other programs call from the command line.

The interesting part is not the operations, it is that everything else in the assignment
depends on this one class being correct: allocation, copying, destruction and the boundary
of every region the operations touch.

The solution

The image is a dynamic matrix of byte with its own copy constructor, assignment operator
and destructor, and pixels reachable two ways: by (row, column) and by a single index over
the unrolled image, which is what makes the whole-image operations one loop instead of two.

Operation What it does Program
Invert Negative negativo
AdjustContrast(in1, in2, out1, out2) Linear contrast stretch between two ranges contraste
Mean(i, j, height, width) Average of a region used by Subsample
Subsample(factor) Icon: each pixel is the mean of a factor × factor block icono
Crop(row, col, height, width) Sub-image subimagen
Zoom2X() Doubles a square region by interpolation zoom
ShuffleRows() Pseudo-random row permutation, seeded by the number of rows barajar

ShuffleRows is deterministic on purpose: the permutation depends only on the number of
rows, so a shuffled image can be un-shuffled and the efficiency study can be repeated.

Layout

include/                image.h and imageIO.h
src/                    the type, the low level PGM I/O and one main per program
src/efficiency-study/   the ShuffleRows study: two mains, the scripts and the measurements
data/img/               sample images
data/expected/          reference outputs from the online judge of the subject
docs/                   the efficiency analysis and the images of this README
tools/run-tests.sh      runs every program and checks what can be checked

Requirements

  • CMake 3.16 or later and a compiler with C++14.
  • Doxygen, only for the documentation.
  • imagemagick and gnuplot, only for the efficiency study.

Build and run

cmake -S . -B build
cmake --build build -j"$(nproc)"

./build/negativo  data/img/vacas.pgm negative.pgm
./build/contraste data/img/vacas.pgm contrast.pgm 100 150 0 255
./build/icono     data/img/vacas.pgm icon.pgm 4
./build/subimagen data/img/vacas.pgm crop.pgm 10 10 100 100     # row col height width
./build/zoom      data/img/vacas.pgm zoom.pgm 50 50 80          # row col side
./build/barajar   data/img/board.pgm shuffled.pgm

bash tools/run-tests.sh build

Results

tools/run-tests.sh is what the CI runs on every push:

ok    negativo matches data/expected/negativo_pub.pgm
ok    contraste
ok    icono
ok    zoom
ok    barajar
ok    subimagen 80 rows x 60 cols
known subimagen 60 rows x 80 cols crashes, as documented
all checks passed

negativo is the only program that can be compared byte for byte, because it takes no
parameters: its output is identical to the reference image from the judge. The other
reference images were produced by the judge with arguments it does not publish, so for those
the check is that the program runs and writes a valid PGM.

The efficiency study measures ShuffleRows on five images and writes time against pixel
count to src/efficiency-study/datos.txt; the theoretical analysis is in
docs/efficiency-study.pdf.

What I learned

  • Managing memory by hand is where the bugs live. The operations are a handful of loops; the
    copy constructor, the assignment operator and the destructor are what decide whether the
    program survives.
  • Two ways of indexing the same buffer pay off. Whole-image operations become a single loop
    over size(), and only the ones that care about geometry use (row, column).
  • Limitations, kept as handed in:
    • Crop crashes when the crop has fewer rows than columns. subimagen … 0 0 60 80
      segfaults, while 0 0 80 60 and any square crop work: rows and columns are swapped
      somewhere in the copy. The test script asserts the crash instead of skipping it, so if
      it is ever fixed the script fails and says the README is out of date. It is not patched.
      The reference image subimagen_pub.pgm is 80 by 60, so this is exactly the case the
      judge tested.
    • icono and zoom produce valid images but do not reproduce the reference ones. Without
      the arguments the judge used, there is no way to tell whether that is a defect or a
      different invocation, so the README does not claim either.
    • The scripts of the efficiency study use relative paths from the old layout and need
      their paths checked before running.
    • Identifiers, comments and Doxygen documentation are in Spanish.
    • The assignment statement written by the teaching staff, and its submission script for
      the online judge, are not published here.
