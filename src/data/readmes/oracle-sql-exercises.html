A basketball league database in Oracle, plus the full set of SQL exercises from the course:
schema, seed data, twenty delivered queries and 136 more pulled out of the chapter notes. CI
creates the tables, loads the rows and runs every delivered query against a real Oracle.

Context

Coursework for FBD — Database Foundations, year 3 of the double degree in Computer
Science and Business Administration, University of Granada (2024–2025). Solo work.

The problem

Design and query a small league database. Four entities and the rules that tie them
together:

  • Equipos — a team has a unique name, a home town, a coach and a founding date.
  • Jugadores — a player belongs to exactly one team.
  • Encuentros — a match is played between a home team and an away team on a date, with
    a score for each side.
  • Faltas — a foul happens in a given match, committed by a given player, in a given
    minute.

Then answer twenty questions about it: who has never fouled, who plays alongside whom,
which team scored most, which matches are still to be played.

The solution

Constraints carry names. Every primary key, foreign key, unique and check constraint in
01-schema.sql is declared with an explicit name:

codE VARCHAR(5) CONSTRAINT PK_codE PRIMARY KEY,
nombreE VARCHAR2(30) CONSTRAINT uq_nombreE UNIQUE NOT NULL,

Oracle would generate a name on its own — SYS_C0011234. Naming them means an error
message says which rule you broke, and ALTER TABLE ... DROP CONSTRAINT has something to
refer to.

The composite key is the match itself. Encuentros is keyed on
(ELocal, EVisitante, fecha) rather than a surrogate id, so the same two teams playing
twice on different dates is legal and the same fixture twice on one date is not. Faltas
then has to carry that whole key plus the player: a four-column primary key
(codJ, ELocal, EVisitante, fecha) and a three-column foreign key back to the match. It is
more verbose than an id column, and it is the reason the database cannot hold a foul that
belongs to no match.

"All of them" is written as "none that is not". SQL has no operator for universal
quantification, so teams that won every home match becomes teams for which no home match
exists that they did not win:

SELECT E.codE, E.nombreE
FROM Equipos E
WHERE NOT EXISTS (
    SELECT 1 FROM Encuentros Enc
    WHERE Enc.ELocal = E.codE AND Enc.PLocal <= Enc.PVisitante)
AND EXISTS (
    SELECT 1 FROM Encuentros Enc
    WHERE Enc.ELocal = E.codE);

The second EXISTS is the part that is easy to miss: without it, a team that has never
played at home vacuously satisfies the first condition and shows up as having won
everything.

Fixtures that do not exist yet come from a WITH clause. To list unplayed matches you
first need the set of all possible ones, which is not in any table. A CTE builds the cross
product of teams against themselves, and NOT EXISTS subtracts the matches already played.

Most of the course SQL was trapped in a document. The chapter notes hold 136 fenced
sql blocks: the whole syllabus, from CREATE TABLE to GRANT. As Markdown none of it
could be parsed or run. tools/extract-from-notes.py writes it out as one file per chapter,
keeping each block's heading and exercise number so a statement can be traced back.

Grouping by chapter rather than by block matters: the median block is three lines, so a file
per block would be 136 fragments. Seven blocks document the grammar rather than run —
UPDATE t SET a = v [WHERE <cond>]; — and are written out commented, so the chapter still
parses as SQL.

CI runs the SQL, it does not just read it. A parser accepts a query against a column
that does not exist. The run job starts gvenzl/oracle-free, executes the schema, commits
the seed data, checks the row counts and then runs all twenty queries. If a join condition
is wrong, the build fails. A second check regenerates src/exercises/ and fails if it no
longer matches the notes.

src/01-schema.sql       4 tables with named constraints
src/02-seed.sql         4 teams, 20 players, 10 matches, 11 fouls
src/03-queries.sql      20 query exercises with their statements
src/exercises/          136 blocks from the course notes, one file per chapter
src/workbook/           earlier chapter work, on an older version of the schema
notes/ApuntesFBD.md     the write-up src/exercises is generated from
tools/                  the extractor and the runner used by CI

src/exercises/ covers the whole course, chapter by chapter:

File Blocks Topic
chapter-1-schema-definition.sql 1 CREATE TABLE, data types
chapter-2-data-maintenance.sql 15 INSERT, UPDATE, DELETE, dates
chapter-3-queries.sql 109 joins, aggregation, subqueries, set operators
chapter-4-views.sql 7 the external level: views

src/01-schema.sql → 02 → 03 is a pipeline: run them in order.

src/workbook/chapters-1-2.sql is separate on purpose. It builds Equipos with
codE VARCHAR2(3) while the delivered schema uses VARCHAR(5): it is the earlier
iteration from chapters 1 and 2, kept as it was handed in. Running it against the same
database as src/ would clash.

Requirements

  • Oracle Database 23ai Free — or any Oracle. CI uses the gvenzl/oracle-free:slim
    container.
  • Python 3.12 with oracledb for the runner. Thin mode, so no Oracle client needed.
  • sqlfluff for the parse check.
pip install oracledb sqlfluff

Build and run

make check       # parse plus drift check, what CI runs
make parse       # every script parses as Oracle SQL
make extract     # regenerate src/exercises from the notes
make diff-check  # fail if the two have drifted apart
make lint        # style rules, reported not enforced

Against a real database:

make db-up       # start Oracle in Docker, takes a couple of minutes
make run         # schema, seed data and all twenty queries
make db-down

make run reads ORACLE_DSN, ORACLE_USER and ORACLE_PASSWORD, defaulting to the
container above.

What I learned

  • Naming constraints costs nothing and pays every time something breaks. The first
    version of the schema let Oracle name them. The first failed insert produced
    ORA-02290: check constraint (SYS_C0011234) violated, which tells you nothing.
  • A composite primary key is a modelling decision, not a shortcut. Keying Encuentros
    on the two teams and the date is what makes a duplicate fixture impossible without a
    single trigger. The cost lands on Faltas, whose foreign key is four columns wide.
  • "Every" is a double negation, and the empty case is where it bites. Writing won all
    home matches     as no home match that was not won is the easy half. The half I got wrong
    first is that a team with no home matches at all passes that test, so the query needs a
    second EXISTS to rule it out.
  • Parsing is not testing. sqlfluff was happy with a query that referenced a column I
    had renamed. Running it against a real Oracle caught it in a second, which is why CI now
    does that.
  • Notes are not a place to keep code. Four fifths of the SQL I wrote for this course sat
    in a Markdown document where nothing could parse it, run it or check it. Pulling it out
    was thirty lines of Python. Not doing it for a year was the mistake.

Known limitations

  • No PL/SQL. Despite what a repository about Oracle might suggest, there are no stored
    procedures, functions, triggers or packages here. The course covered DDL, DML, queries,
    views, the catalogue and indexes. The name of this repository says sql for that reason.
  • The queries are checked for execution, not for correctness. CI proves each one runs
    and returns rows. Nothing asserts that the rows are the right ones — that would need
    expected result sets, which were never written.
  • src/exercises/ is parsed, not executed. Those chapters query the example databases
    used in the course notes — plantilla, proveedor, pieza, ventas — and no schema for
    them survives. Only the basketball pipeline runs against Oracle.
  • Seven blocks in src/exercises/ are commented out. They document SQL grammar
    (UPDATE t SET a = v [WHERE <cond>];) rather than being runnable, and are marked
    syntax, not runnable.
  • src/workbook/scratch-template.sql and scratch-first-table.sql are not SQL. They
    hold DESCRIBE, a SQL*Plus client command, so no SQL parser reads them. They are listed
    in .sqlfluffignore and skipped by make parse. Nine lines of scratch, kept because
    they were part of the submission.
  • The seed data is small on purpose: 4 teams, 20 players, 10 matches. Enough to make
    every query return something, not enough to say anything about performance.
  • Style rules are disabled, see .sqlfluff. Reformatting delivered coursework to
    satisfy a linter would misrepresent what was handed in.
