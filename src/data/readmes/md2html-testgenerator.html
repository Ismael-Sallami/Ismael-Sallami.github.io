Turns questions written in plain Markdown into a self-marking HTML quiz: it shuffles them,
marks them, shows the explanations and runs from a single file with no server behind it.

There is a browser version, with nothing to install:
elblogdeismael.github.io/md2html — drop
in a .md, pick a theme and download the quiz. It converts in your browser, so the file
never leaves your machine.

Context

A tool of my own, not coursework. Practising for an exam means having questions to answer,
and the ones you find are scattered across platforms that lock them in. Writing them in
Markdown takes a minute; turning them into something you can actually sit and answer, with
marking and an explanation per question, took this.

It is also what generates the practice tests published with my notes.

The problem

An HTML quiz is not hard to write. It is hard to write twenty times, which is what it
takes to be worth using: every question needs its options, its right answer wired to the
marking, and its explanation hidden until it is asked for.

The audience is not programmers. A teacher building a listening exercise should write the
question and drop the audio next to it, not open a <label>.

The solution

A Markdown dialect with three rules, which is all a question needs:

1. Which of these is a markup language?

    - (x) Markdown
    - ( ) Python

    > Markdown marks structure up. Python is a programming language.

The number is decorative: the output renumbers everything, so questions can be reordered or
pasted in from anywhere. (x) is the right answer. A > line is the explanation, and it
turns into a button. Full syntax in docs/syntax.md.

One HTML file, self-contained. Marking, exam mode, dark mode and explanations are the
template's own JavaScript. Nothing is fetched at run time, so the result works from a USB
stick, from a virtual campus or opened with file://.

Audio and video are a keyword, not a syntax. ![audio](clip.mp3) and
![video](clip.mp4) become <audio controls> and <video controls>, which is what makes a
listening exercise possible without the writer touching HTML. The alt text is the switch:
anything else stays an image.

Twelve themes, one behaviour. They differ in the palette and in nothing else, so
choosing one never costs a feature. src/md2html/templates/ is the source for both this
tool and the web version: scripts/export_templates_js.py embeds them into the JavaScript
the site loads, which is why there is one place to edit a theme rather than two.

The conversion knows nothing about tkinter. core.py parses and renders; gui.py is
the window. That split is what lets the CI convert the sample quiz and read the result on a
machine with no display.

Layout

md2html.py                  launcher: python3 md2html.py opens the window
src/md2html/core.py         parsing and rendering, no display needed
src/md2html/gui.py          the tkinter window
src/md2html/templates/      the twelve themes, pro.html being the default
scripts/export_templates_js.py   exports them for the browser version
examples/questions.md       a quiz using every supported element
examples/questions.html     what it produces
examples/media/             the audio, video and image that quiz refers to
examples/previews/          six finished quizzes, one per theme
docs/syntax.md              the syntax, in full
tests/test_core.py          conversion tests

Requirements

  • Python 3.12
  • markdown 3.5+
  • tkinter, only for the window. It ships with Python but is a separate package on Debian
    and Ubuntu: sudo apt install python3-tk

Build and run

git clone https://github.com/Ismael-Sallami/md2html-testGenerator.git
cd md2html-testGenerator

python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

python3 md2html.py

The window asks for three things: the .md with the questions, the theme, and where to save
the quiz. Optionally a second .md whose content is shown as notes at the top.

Converting without opening a window, which is what the tests do:

import sys; sys.path.insert(0, "src")
from md2html import core

core.generar_html_final("examples/questions.md", "quiz.html", "", True, False)

Running the tests:

pip install pytest ruff
pytest -q
ruff check .

Results

examples/questions.html is the sample quiz, generated from
examples/questions.md: eight questions with an image, a formula,
a multiple-answer one, a table, a code block, audio and video.

The six themes below are finished quizzes in examples/previews/. Open them in a browser
to answer them.

The CI converts the sample on every push and checks the result: eight questions, renumbered
in order, the right options wired to the marking, the explanations behind their button, and
the twelve themes resolving to a file that exists.

What I learned

  • Making the numbers you type meaningless was the change that made the format usable.
    Anything that has to stay consistent by hand stops being consistent by the third edit.
  • A shared source beats a synchronised copy. The themes live once and the web version is
    generated from them, so a theme cannot be right in one place and stale in the other.
  • Splitting the window off from the conversion is what made the tool testable at all. It is
    the same code as before; it just no longer needs a screen to run.
  • Limitations:
    • Tables and code blocks do not survive. Options are joined into a single line
      before Markdown runs, and both need lines of their own. A table comes out as pipes and a
      fenced block as inline <code>. Pasting them as an image is the way round it, and the
      tests assert this too.
    • There is no command line: converting without the window means importing core.
    • The window, the theme names and the generated quizzes are in Spanish. They are what the
      reader sees, and the quizzes are for Spanish subjects.
    • The tests cover the conversion, not the interface. Testing tkinter needs a display, and
      the window is a form over one function.
